## 3. 模块和数据流

`CLI/Gradio → service → ToolCallingAgent → record_plan/四个领域工具 → 最终回答`

知识数据流：`Markdown/TXT → doc_id/来源/哈希 → 分段 → 字符TF-IDF → hits → 工具observation → 下一次模型请求 → 来源引用`。
数值数据流：`任务 → 结构化计划 → convert_units → 已成功output → 引用解析 → calc_heat_duty → 最终回答`。
框架负责模型调用与迭代；execution.py 仅管理项目计划、参数依赖和状态。计划变更保留版本，已成功步骤不可删除或改写；失败尝试留痕，可修正重试。
任务声明每个显式参数的输入来源；`user:` 说明由模型生成，需核对题设。程序对 `s2.value` 执行真实解析，能够证明结果回用。

## 4. 你短期需要准备什么

- 确认源码公开/共享的授权范围。合同第7页第八条第4款存在新增交付源码公开传播限制，若尚无双方另行书面安排，应先厘清；本轮未执行上传。
- 准备 GitHub 账号、协作者准确用户名，按 GITHUB_UI.md 完成组织空仓库与 Admin 邀请。
- 准备服务器系统、登录方式、可写项目目录、Conda 是否已有、联网情况；不需要现在在本机安装依赖。
- 确定可用模型服务：model ID、兼容地址、工具调用支持、超时限制。密钥只在服务器 `.env` 输入。
- 审阅15张自编知识卡和三个演示题，确认是否有要替换的授权专业资料及来源。
- 安排实际案例验证并填写研究报告。图片要求“研究报告一份”，当前模板不等于报告已经完成。

## 5. 后续开发人员交接

从 README、ACCEPTANCE、tools.py、execution.py、agent.py、service.py 开始。先验证 v1.26.0 与所选服务工具协议，再补充功能。
优先排查错误：百分比/质量分数混淆、温度/温差混用、比热无依据、依赖未成功却执行、模型抄写而未引用、步数耗尽被标成功、引用存在但内容不支持结论。
不要用当前框架的存在、静态审阅或一条可运行命令冒充验收结果；每个结论应引用实际 run_id。
